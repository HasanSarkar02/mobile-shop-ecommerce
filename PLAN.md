    25.1. [x] **Courier status → order status (R3, 2026-08-24).** A courier "delivered" used to move the fulfillment only, leaving the order at Shipped forever. `OrderService::updateFulfillment()` now locks the parent order then the fulfillment (parent-before-child, the same hierarchy convention as `stock_items → serial_numbers`) and calls a private `propagateFulfillmentToOrder()`, so all three callers — the admin action, `CourierService::syncStatus`, and the hourly command — get the propagation from one place:
        - **every** consignment Delivered and the order is Shipped → the order transitions to Delivered. *Every*, not *this one*: split stock/preorder fulfillments legitimately deliver at different times.
        - every consignment Delivered but the order never reached Shipped → logged, **not** transitioned. Synthesising a Shipped event to reach Delivered would put false history in `order_events`.
        - the order is already Delivered/Refunded/Cancelled → silent no-op. A repeat poll must never throw, and a courier report must never resurrect a cancelled order.
        - **every** consignment Failed → raises `FinancialAdjustmentRequired` and **changes nothing else** (locked decision). Cancellation restocks, releases the coupon and is one-way — `Cancelled → Delivered` is forbidden — so a courier status flip-flop would be unrecoverable. Staff cancel or reship deliberately.
        - **some** consignments Failed → `FinancialAdjustmentRequired` naming the failed consignment; partial delivery is real and the model has no per-consignment cancellation.
        Every propagation log is written through `logPropagationOnce()`, keyed on `metadata->propagation`, so an hourly poller observing the same state for days cannot spam the timeline. No inventory moves on delivery — stock was committed at Confirmed. Covered by `tests/Feature/Orders/FulfillmentStatusPropagationTest.php`.
    25.2. [x] **COD cash recording (R3, 2026-08-24).** A COD order used to carry **zero** `order_payments` rows for its entire life. It still creates none at checkout — cash genuinely has not been collected — but delivery now has a collection event: `OrderService::recordCodCollection()` records it through `recordPayment()` with the derived reference `cod:{fulfillment_id}`, which turns the existing unique `(tenant_id, transaction_reference)` index into the idempotency key, and returns `null` (silent no-op) rather than throwing on a repeat. **The poller does not book money** (locked decision): it sets the order to Delivered, and a "Record COD Collection" action on `ViewOrder` pre-fills the due for staff to confirm — couriers report delivered before remitting, and collecting less than the full due is common. `recordPayment()` itself was also fixed to lock the order row: it read `amountPaid()` and then wrote against it with no lock, so two concurrent recordings could both pass the remaining-due guard, and the unique index cannot backstop cash because MySQL treats every NULL reference as distinct. Covered by `tests/Feature/Orders/CodCollectionTest.php` + `tests/Feature/Orders/OrderCodRefundActionsTest.php`.
